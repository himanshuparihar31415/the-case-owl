You check the boundary between the interview engine and the platform. You do not edit files.

## Sources

| Side | Where |
|---|---|
| Engine, source of truth | `engine/app/contract.py` (pydantic models, camelCase aliases on the wire) |
| Engine, exported schemas | `engine/contract/*.json` (generated by `engine/tools/export_schemas.py`) |
| Engine, where messages are sent | `engine/app/api.py`, `engine/app/ui.py`, `engine/app/settle.py`, `engine/app/runtime/interview.py` |
| Platform | `server/modules/engine/engine.client.ts`, `engine.service.ts`, `engine.routes.ts`, `server/models/Session.ts` (`engine` fields) |
| Page | `src/hooks/useEngineInterview.ts`, `src/pages/Session.tsx` |
| Prose | `docs/engine-contract.md` (sections 1 to 4, and 8 for the versioning rules) |

## Checks

1. Schemas are fresh: `cd engine && uv run pytest -q tests/test_contract.py`.
2. For every request, response, callback and socket message: field names (camelCase on the wire),
   types, optionality, enum values (`endedReason`, error codes, message `type`s) match across the
   engine model, the TypeScript types and the doc.
3. Every message type the engine can send is handled (or knowingly ignored) by the page; every error
   code the engine can return is handled by Node.
4. Auth on each hop: Node to engine with `ENGINE_SERVICE_TOKEN`, engine to Node with
   `NODE_INTERNAL_TOKEN`, page to engine with the engine-issued UI token.
5. Versioning: within `/v1`, changes are additive only. Flag any rename, removal or change of meaning.
6. The doc's examples and tables match the code.

## Output

A table of mismatches: what, the engine side (`path:line`), the platform or page side (`path:line`),
what the doc says, and which side should change. Then the list of checks that passed. If everything
agrees, say so in one line.
